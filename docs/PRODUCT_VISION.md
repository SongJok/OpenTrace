# OpenTrace 产品愿景：企业组织操作系统

## 愿景

OpenTrace 要成为企业的 **AI 原生组织操作系统**：把分散在对话、文档、数据库、会议、任务和审批中的工作，收敛为可恢复、可审计、可授权的人机协作过程。AI 不替代组织责任，而是承担信息整理、初稿生成、受控执行和持续值守；员工从重复操作转向判断、复核、决策与例外处理。

这不是一个“会聊天的工具箱”。产品的最小单位是一次有上下文、有证据、有权限边界、有运行状态的工作；事实来源是 PostgreSQL 中的 Response、Item、Event、Outbox、Approval 和工具账本，模型正文不能替代业务证据。

## 第一灯塔：可信经营报告

首个高价值闭环是“数据洞察、经营月报、经营简报”。它同时验证 OpenTrace 的核心复用能力：

1. DataAgent 在 Project 授权的数据源中执行只读 SQL，并返回口径、rows 和 verification report。
2. RAG 只检索当前用户可访问的已发布知识，为制度与业务约束提供引用。
3. 图表使用 DataAgent 返回的 rows 与 visualization config，可回到原始 SQL 复核。
4. TaskDefinition 按 RRULE 调度，TaskRun 与 Response 一一关联，客户端离线不影响执行。
5. Worker 从持久化工具账本投影报告产物；缺 SQL、校验、必要引用或图表时标记“需复核”。
6. 所有写操作仍进入 ResponseApproval；报告能力本身不获得隐式写权限。

这一场景的北极星指标不是“生成了多少篇文字”，而是 **按时交付且证据完整、被业务负责人采纳的报告比例**。

## 产品原则

- **事实优先**：数据库记录与已发布知识是事实；模型输出是解释与建议。
- **人在责任链上**：AI 可以执行只读工作；写入、外发、删除和高风险决策必须审批。
- **一次定义，持续运行**：对话中的成功过程可沉淀为 Project、Goal、Task、Skill 或 Alert。
- **范围默认收紧**：所有读取同时受 user、tenant、workspace、Project 与资源 ACL 约束。
- **失败可见且可恢复**：断流不取消 Response，Redis 丢失不丢事实，未知副作用进入 reconciliation。
- **评价真实结果**：fixture 只验证评测合同；Beta 放量必须使用真实 Responses 主链结果。

## 分阶段产品重点

### P0：Responses 企业 Beta

完成企业准入、租约恢复、审批暂停、工具幂等、事件续传、token/成本结算、租户隔离、真实评测与发布门禁。停止扩张第二套运行时。

### P1：经营报告灯塔

把数据洞察、月报和经营简报做成独立工作面，跑通配置、试运行、周期执行、证据复核、通知和追溯。

### P2：组织协同

在同一运行时上接入会议、邮件、客服、法务与财务流程；通过 Connector 和 Skill 扩展输入输出，不改变事实源与审批语义。

### P3：数字员工组合

以 Goal 和可版本化 Skill 组合跨天工作，增加责任人、SLA、成本预算、交接和组织级运营视图。只有达到容量、灾备和安全评审门槛后进入 GA。

完整目标架构与领域契约见 [企业组织操作系统架构](architecture/enterprise_organization_os.md)。
