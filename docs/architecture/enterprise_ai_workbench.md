# 企业 AI 工作台架构

## 愿景

OpenTrace 的企业化目标不是把多个 AI 功能堆叠成菜单，而是成为“企业级的工作台、最懂公司的 AI”。员工应从一个统一入口看到当前业务上下文、可信知识、授权数据、正在执行的 AI 工作、需要人工确认的动作以及主动发现的业务异常。

## 产品分层

```text
企业 AI 工作台 /work
  ├─ 员工行动面：待审批、关键预警、失败重试、最近工作
  ├─ 统一行动中心：分类、搜索、未读通知确认与站内处置跳转
  ├─ AI 就绪度：上下文、知识、数据、自动化、安全治理
  ├─ Project：业务目标、指令、记忆与数据权限边界
  ├─ Goal：通过 Responses 主链路持续执行的长期工作
  └─ 专业入口：企业知识库、数据工作台、定时任务、治理中心

Responses 主链路
  └─ PostgreSQL Response / Item / Event / Approval / Outbox 是执行事实源

企业能力控制面
  ├─ /knowledge       知识治理
  ├─ /databases       数据接入与语义治理
  ├─ /permissions     权限与企业宪法
  └─ /audit           审计
```

工作台不是第二套 Agent Runtime，也不直接执行模型、工具或后台任务。`GET /api/v2/workbench/overview` 只从 PostgreSQL 事实状态生成当前用户的可行动投影；Redis 不参与状态判定。`attention_limit` 允许行动中心在 5 到 100 条之间按需读取队列，同时保持服务端边界过滤；通知已读仍通过持久化通知 API 更新，不由前端本地状态冒充完成。

## 隔离与安全

每类资源都同时保留 `user_id`、`tenant_id` 和 `workspace_id` 边界。共享企业数据与知识不使用“本用户拥有”替代授权判断：

- 数据源复用统一 `accessible_data_sources_statement()`，同时支持 Owner 和显式资源授权。
- 企业知识复用 `resolve_access_context()` 与 `accessible_source_predicate()`，执行空间角色、组织主体、细粒度 ACL、密级和有效期判断。
- 知识治理健康度只聚合 Reviewer 可治理的空间。
- 工具审批通过 `ResponseApproval → ResponseRecord` 连接后再次校验用户、租户和工作区。
- 通知只统计当前作用域内员工拥有的定时任务与预警规则。

## 企业 AI 就绪度

就绪度是可解释的建设指标，不参与模型权限决策，也不能绕过治理：

| 维度 | 含义 |
| --- | --- |
| 业务上下文 | 是否建立 Project、业务指令、角色和数据绑定 |
| 企业知识 | 是否拥有可访问知识空间和已发布可信知识 |
| 企业数据 | 是否存在当前员工有权访问的有效数据源 |
| 主动工作 | 是否使用 Goal、定时任务或主动预警 |
| 安全治理 | 待审批、关键预警、执行失败和知识治理健康度 |

每个缺口必须返回明确的 `code`、说明和站内处理路径，避免只展示不可行动的总分。

## 后续演进

1. 引入组织级工作台模板，根据部门、岗位和 Project 自动配置入口与推荐任务。
2. 将知识反馈、审核、同步失败和 Goal 里程碑统一投递到企业通知中心，并接入邮件、钉钉等渠道。
3. 增加效果度量：任务完成时长、人工接管率、知识命中率、引用覆盖率和节省工时。
4. 建立管理员运营面，按租户和工作区查看采用率、成本、质量、风险和 SLA。
5. 为超大租户增加工作台聚合快照；快照仅作可失效投影，PostgreSQL 仍是事实源。
