# 企业 AI 工作台架构

## 愿景

OpenTrace 的企业化目标不是把多个 AI 功能堆叠成菜单，而是成为“企业级的工作台、最懂公司的 AI”。员工应从一个统一入口看到当前业务上下文、可信知识、授权数据、正在执行的 AI 工作、需要人工确认的动作以及主动发现的业务异常。

这里的“懂公司”由[企业认知底座](enterprise_cognition.md)承载：公司和部门是一等认知实体，稳定基础信息通过审核发布的版本进入 Responses 上下文，制度细节继续由绑定的企业知识空间按权限检索并提供引用。员工聊天、个人记忆和未发布草稿不能直接升级为公司事实。

## 产品分层

```text
企业 AI 工作台 /work
  ├─ 今日工作脉搏：确定性优先级、逾期自动化、Goal 停滞与统一时间线
  ├─ 工作续接：按持久会话合并 Response / Goal，并给出精确下一步
  ├─ 员工行动面：待审批、关键预警、失败重试、最近工作
  ├─ 统一行动中心：分类、搜索、未读通知确认与站内处置跳转
  ├─ 企业工作场景：前置条件、能力链、记忆、证据、审批与可验收交付物
  ├─ AI 就绪度：上下文、知识、数据、自动化、安全治理
  ├─ Project：业务目标、指令、记忆与数据权限边界
  ├─ Goal：通过 Responses 主链路持续执行的长期工作
  ├─ Calendar：个人日程、重复安排、提醒与时间型记忆
  └─ 专业入口：企业知识库、数据工作台、定时任务、治理中心

Responses 主链路
  └─ PostgreSQL Response / Item / Event / Approval / Outbox 是执行事实源

企业能力控制面
  ├─ /knowledge       知识治理
  ├─ /databases       数据接入与语义治理
  ├─ /permissions     权限与企业宪法
  └─ /audit           审计
```

工作台不是第二套 Agent Runtime，也不直接执行模型、工具或后台任务。`GET /api/v2/workbench/overview` 只从 PostgreSQL 事实状态生成当前用户的可行动投影；Redis 不参与状态判定。`attention_limit` 允许行动中心在 5 到 100 条之间按需读取队列，同时保持服务端边界过滤；通知已读仍通过持久化通知 API 更新，不由前端本地状态冒充完成。

### 今日工作脉搏

`operating_pulse` 把“工作台有什么”提升为“员工今天先处理什么”。它使用请求传入的 IANA
时区计算本地自然日，并把以下 PostgreSQL 事实合并到同一投影：

- `ResponseApproval`、未确认 `AlertEvent`、失败或不完整 `ResponseRecord`；
- 未读 `TaskNotification` 与知识治理待办；
- 当日 `CalendarEvent`（包含重复日程展开结果）；
- 当日应运行或已经逾期的 `TaskDefinition` / `AlertRule`；
- 超过 72 小时没有检查点或状态更新的活动 `GoalRun`。

优先级为可解释的确定性规则：风险级别、事项类型、等待时长和逾期时长共同生成
`priority_score` 与 `P0-P3`，并返回 `priority_reason`。关键预警和严重逾期可进入 P0；审批、
失败执行和长时间停滞的 Goal 按等待时间升级。相同资源已有更直接的预警或逾期事项时，
通知不重复占用今日焦点。该分数只影响读取排序，不改变审批状态、任务调度或 Worker 重试。

时间线同时展示个人日程、报告/定时任务和指标检查。摘要计数基于服务端读取的当日集合
（重复日程最多展开 200 项），列表再按企业上限截断，避免 UI 限制造成错误经营判断。API 的 `timezone` 默认值为 `Asia/Shanghai`，
非法时区返回参数错误；前端显式传递产品时区，不能按浏览器本地缓存自行重算事实日界。

### 工作续接

工作台不再把每个 Response 和 Goal 当作互不相关的“最近动态”。服务端以未归档、非临时的
`ChatSession` 为工作上下文边界，将同一会话的最新 Response 与关联 Goal 合并为一项工作，
并保留 Project 名称、Response / Goal 标识和最后更新时间。最新 Response 的审批、失败或执行中
状态优先于 Goal 的笼统运行态，避免把真实阻塞显示成“进行中”。

下一步由持久状态确定：`requires_action` 进入审批，`queued / in_progress` 查看进度，
`failed / incomplete` 检查并重试，暂停 Goal 恢复运行，已完成工作继续下一轮。会话型工作返回
`/chat?conversation=<id>`；聊天页先在当前 user、tenant、workspace 可见会话中解析该 ID，再读取
消息并恢复 SSE，不能仅切换一个前端活动标识。无会话的 Goal 继续进入 Goal 管理页。

场景目录见[企业日常工作场景目录](../catalog/enterprise_work_scenarios.md)。工作台根据当前
Project、已发布知识、授权数据源、个人安装 Skill、可见公司 Skill、Goal、定时任务和预警
生成 `setup_required / ready / active` 状态。场景按钮只负责路由和预填提示词；实际执行仍由
Responses Worker 完成，不能绕过工具审批、幂等账本、资源边界或记忆治理。

## 连续对话与个人日历

短追问不能只按当前一句重新规划。ContextAssembler 先沿当前 Response 父链装配最近对话、工具调用和工具结果；规划器获得其中的精简投影。对于“确认、继续、执行”等表达，Worker 会继承上一轮尚未产生工具结果的副作用调用，并继续走持久化审批，不会把“确认创建”扩展成定时任务、数据预警等无关能力。

个人日历写入采用确定性准备与审批执行分离：当请求包含可可靠解析的日期、时间范围和明确写入动作时，Worker 直接生成 typed `create_calendar_event` 调用及 `ResponseApproval`，但不会在审批前执行。批准后仍通过工具账本和幂等键执行一次；模糊日期或缺少时间时回到模型澄清。日历查询属于一级时间记忆，未来两周的已确认事件可由 ContextAssembler 直接注入，避免后续追问再次依赖模型选择工具。

能力目录只向规划器暴露正相关能力和调用方显式工具。能力候选不隐含执行顺序，自动计划不会把无关能力机械串成依赖；未执行步骤标记为 `skipped`，不能伪装成 `completed`。疑问句默认禁止扩大为写操作，只有明确动作请求或对待处理动作的确认才能进入审批。

历史上误存为用户记忆的助手 `Q:/A:` 整段输出会被质量门禁隔离。包含旧 Cognitive Kernel 自述的无来源记忆由 `r0008_memory_quality_cleanup` 统一标记为拒绝，避免退役架构描述继续污染企业上下文。

## 隔离与安全

每类资源都同时保留 `user_id`、`tenant_id` 和 `workspace_id` 边界。共享企业数据与知识不使用“本用户拥有”替代授权判断：

- 数据源复用统一 `accessible_data_sources_statement()`，同时支持 Owner 和显式资源授权。
- 企业知识复用 `resolve_access_context()` 与 `accessible_source_predicate()`，执行空间角色、组织主体、细粒度 ACL、密级和有效期判断。
- 知识治理健康度只聚合 Reviewer 可治理的空间。
- 工具审批通过 `ResponseApproval → ResponseRecord` 连接后再次校验用户、租户和工作区。
- 通知只统计当前作用域内员工拥有的定时任务与预警规则。

### 企业问答访问矩阵

企业问答统一采用“执行主体 + 企业作用域 + 资源授权”三层判定，不能由模型参数、历史结果或
客户端传入 ID 放宽：

| 主体 | 可问答知识 | 不可越过的边界 |
| --- | --- | --- |
| 普通员工 | 本人文档；有权访问的知识空间中满足来源 ACL、密级、有效期且已发布的知识 | 其他用户私有文档、未授权空间、超密级来源、其他租户或工作区 |
| 管理员 | 当前租户和工作区内全部可问答文档与知识来源 | 其他租户或工作区；管理员全量读取不自动授予编辑、删除或发布权限 |

`role=admin` 与 `is_superuser=true` 使用同一管理员判定，避免控制面和问答面权限分叉。原始
文档兜底通过服务端用户记录判定管理员，不能信任 Agent 或模型传入的布尔值。知识页检索
继续只读取已发布的活动版本；失效、撤回和删除来源对管理员同样不可见。

多轮对话的 Response 父链、热知识状态、上下文装配和记忆学习都绑定同一个
`user_id + tenant_id + workspace_id + conversation_id` 四元组。任一字段失配时停止继承并
返回空或终止当前 Response，不能用猜测的 Conversation ID 读取其他员工的历史、结果或
记忆。管理员的企业知识读取能力也不会扩大为读取其他用户的个人记忆；个人、Project 和
Conversation 记忆继续按当前 Response 主体隔离。

## 企业 AI 就绪度

就绪度是可解释的建设指标，不参与模型权限决策，也不能绕过治理：

| 维度 | 含义 |
| --- | --- |
| 业务上下文 | 是否发布公司/部门认知，并建立 Project、业务指令、角色和数据绑定 |
| 企业知识 | 是否拥有可访问知识空间和已发布可信知识 |
| 企业数据 | 是否存在当前员工有权访问的有效数据源 |
| 主动工作 | 是否使用 Goal、定时任务或主动预警 |
| 安全治理 | 待审批、关键预警、执行失败和知识治理健康度 |

每个缺口必须返回明确的 `code`、说明和站内处理路径，避免只展示不可行动的总分。

## 后续演进

1. 引入组织级工作台模板，根据部门、岗位和 Project 自动配置入口与推荐任务。
2. 将知识反馈、审核、同步失败和 Goal 里程碑统一投递到企业通知中心，并接入邮件、钉钉等渠道。

## 钉钉企业上下文与 Skill 蒸馏

- 钉钉文档和群聊作为外部证据进入企业知识空间，保留来源、密级、群主体 ACL、同步游标和审计记录；外部内容不能直接成为系统指令。
- 钉钉部门和成员关系进入企业目录，再投影到知识权限主体，使公司/部门认知与实际组织架构保持一致。
- 管理员可在 Skills 页面选择文件或文件夹，将流程、制度、标准和检查项蒸馏成指令型 Skill。生成结果只发布到当前租户和工作区，标记为“公司发布”，并保留文件哈希与来源路径。
- 公司 Skill 不执行来源文件中的代码、宏或脚本；会话显式启用后才进入 Responses 上下文，仍受平台权限、审批、幂等和审计约束。
3. 增加效果度量：任务完成时长、人工接管率、知识命中率、引用覆盖率和节省工时。
4. 建立管理员运营面，按租户和工作区查看采用率、成本、质量、风险和 SLA。
5. 为超大租户增加工作台聚合快照；快照仅作可失效投影，PostgreSQL 仍是事实源。
